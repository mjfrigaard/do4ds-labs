How big does a server need to be? Three resources decide: CPU, RAM, and storage, plus a GPU for some modeling work. The examples come from the t3.micro we’ve been running since Lab 7; scaling it up when it runs short is covered in Instance Size.

How computers work (for data science)

Each comprehension question below asks which part of a computer we’d upgrade to fix a problem. To answer them, it helps to know what each part does. The chapter explains the parts from a system administrator’s point of view. The sections below add the R and Python side, with links to Wikipedia for more depth.

The CPU

The central processing unit (CPU) is the part of the computer that runs your code. Every program, from a Python script to the operating system, is a long list of small instructions. The CPU works through that list in a cycle:

Each trip around this cycle takes a tiny fraction of a second. The number of cycles per second is the clock speed, measured in gigahertz (GHz). A 3 GHz CPU runs about three billion cycles each second. A higher clock speed means each step of your code finishes sooner.

R and Python add a layer between our code and the CPU. Both are interpreted languages, so each line we write turns into many CPU instructions while it runs. Vectorized functions skip most of that work by handing the whole job to compiled C code. The two versions below give the same answer. On my laptop, with a vector of 10 million numbers, the vectorized one runs about 90 times faster in both R and Python:

x <- runif(1e7)
# loop: the interpreter handles every element
total <- 0
for (i in seq_along(x)) total <- total + x[i]
# vectorized: one call to compiled code
total <- sum(x)
import numpy as np
x = np.random.rand(10_000_000)
# loop: the interpreter handles every element
total = 0.0
for value in x:
    total += value
# vectorized: one call to compiled code
total = x.sum()

Before paying for a faster CPU, it’s worth looking for loops like these. Rewriting a loop takes a few minutes; a bigger instance costs money every hour it runs.

Cores

A core is a complete processing unit inside the CPU. A CPU with more than one core is a multi-core processor. Each core runs its own list of instructions, so a four core CPU can work on four tasks at once. Extra cores only help when the work splits into independent pieces:

Most R and Python code runs on a single core unless we tell it otherwise (with packages like {future} in R or multiprocessing in Python). If each step depends on the result of the step before it, the extra cores have nothing to do. This is why faster cores often help more than more cores.

We can check how many cores R and Python can see:

parallel::detectCores()
import os
os.cpu_count()

Both return 2 on the t3.micro, but that count is threads, not cores. AWS sells virtual CPUs (vCPUs), and each vCPU is one hardware thread. The t3.micro has one physical core running two threads, so it shows up as 2 vCPUs.

Some modeling packages use every core without being asked. In R, {ranger} grows random forest trees on all available cores by default. In Python, scikit-learn models with an n_jobs argument use every core when we set n_jobs=-1.

Parallel work has a RAM cost, too. Each worker process usually gets its own copy of the data, so four workers can need close to four times the memory of one.

RAM

Random access memory (RAM) holds the data and code the CPU is using right now. RAM is like the top of a desk: everything on it is within arm’s reach, but the space is limited. RAM is fast because the CPU can read any location in it directly. It’s also temporary, so everything in RAM disappears when the computer turns off.

When we load a dataset in R or Python, the whole thing is copied into RAM. If it doesn’t fit, the session doesn’t just slow down; it crashes. RAM is usually the first resource a data science workload runs out of. The t3.micro we’ve been using has only 1 GB.

A dataset can take up much more room in RAM than it does on disk. Text columns are the usual cause, along with the temporary copies R and Python make while transforming data. We can measure how much memory an object is using with lobstr::obj_size() or df.memory_usage():

lobstr::obj_size(penguins)
df.memory_usage(deep=True).sum()  # bytes

Comparing these numbers to the file size on disk shows how close a dataset is to the limit. The rule of thumb in the first comprehension question leaves room for this gap.

Storage

Storage (a hard drive or solid state drive) keeps files for the long term. If RAM is the desk, storage is the filing cabinet across the room. It holds far more, and it keeps everything when the power is off. The trade off is speed: reading from even a fast solid state drive takes about a thousand times longer than reading from RAM.

Because storage is slower, the computer copies data into RAM before the CPU works on it. On an EC2 instance, storage is an Elastic Block Store (EBS) volume attached to the server. We can make the volume bigger without changing the instance type.

Data science projects fill storage faster than we might expect. Package libraries, virtual environments, saved models, and data files all live there. A single deep learning package like PyTorch can take up several gigabytes on its own. We can see how much room the renv and uv package caches are using with du:

du -sh ~/.cache/R ~/.cache/uv

File format matters, too. A Parquet file is usually much smaller than the same data saved as a CSV. R ({arrow}) and Python (pyarrow) also read it faster, because the data is compressed and stored by column.

GPUs

A graphics processing unit (GPU) is a processor built from thousands of small, simple cores. GPUs were designed to draw graphics, which means running the same calculation on millions of pixels at once. Training a deep learning model involves the same kind of math (large matrix multiplications). A GPU’s thousands of cores can finish that work in hours instead of days.

GPUs come with three catches:

  1. They’re expensive.
  2. Our code has to be written (or configured) to use one.
  3. Code that runs one step at a time gets nothing from a GPU.

Most of the data science toolkit never touches a GPU. {dplyr}, {pandas}, and most of {tidymodels} and scikit-learn run on the CPU. GPUs matter for deep learning frameworks like PyTorch and TensorFlow (and their R interfaces, {torch} and {keras3}), and for a few model libraries like XGBoost. In each case we check that the GPU is visible, then move the work onto it:

import torch
torch.cuda.is_available()
device = "cuda" if torch.cuda.is_available() else "cpu"
model = model.to(device)
1
True if PyTorch can see a GPU
2
Move the model’s weights onto the GPU 
library(torch)
cuda_is_available()
1
TRUE if torch can see a GPU

A GPU also has its own memory (VRAM), separate from the server’s RAM. The model and each batch of data have to fit in VRAM, which brings back the same “does it fit?” question from the RAM section.

Comprehension questions

“Think about the scenarios below. Which part of your computer would you want to upgrade to solve the problem?”

“1. You try to load a .csv file into {pandas} in Python. It churns for a while and then crashes.”

RAM. {pandas} loads the whole file into memory, and transformations make temporary copies on top of that. When the data doesn’t fit, the session crashes instead of slowing down. The chapter’s rule of thumb is to have at least three times as much RAM as the largest dataset:

\[\text{Amount of RAM} \ge 3 \times \text{max amount of data}\]

Before buying more, it’s worth asking whether the whole file needs to be in memory at once. Reading only some columns, or switching to a database or Parquet file, can load far less.

With a 400 MB file as an example, the 3x rule already asks for more memory than a t3.micro has:

“2. You go to build a new ML model on your data. You’d like to re-train the model once a day, but training this model takes 26 hours on your laptop.”

A faster CPU (or a GPU). A 26 hour job can’t run once a day no matter how much RAM or storage the machine has. If the model is parallel (deep learning or tree based models like XGBoost), a GPU is the upgrade that turns days into hours. The chapter’s advice is to try faster CPU cores first.

The order to try things in looks like this:

“3. You design a visualization using the {matplotlib} package and want to create one version of the visualization for each US state. You could do it in a loop, but it would be faster to parallelize the plot creation. Right now, you’re running on a t2.small with 1 CPU.”

More CPU cores. Parallelizing means running several plots at the same time, one per core, and a single core can only run one at a time. Fifty plots on one core is still a loop. A GPU doesn’t help here because {matplotlib} draws on the CPU.

Assume each plot takes one minute. With the same total work, four cores finish in about a quarter of the time:

The chapter’s analogy is a factory that does addition problems. The CPU is the assembly line, RAM is the space next to the line where work waits, and storage is the warehouse next door. The mind map groups the other terms under the resource they describe:

“What are the architectural differences between a CPU and a GPU? Why does this make a GPU particularly good for Machine Learning?”

A CPU has a handful of fast cores, usually 4 to 16 on a laptop. A GPU has hundreds or thousands of slow ones: 700 to 4,000 on a mid range card, each running at 1 to 10 percent of a CPU core’s speed. The CPU is built to finish one problem quickly. The GPU is built to work on thousands of small problems at once.

Training most machine learning models is that kind of work. The same arithmetic repeats over many rows, weights, or trees, and each piece is independent of the others. When work splits that way, the number of cores matters more than the speed of any one core. A GPU can then train in hours what a CPU trains in days.

Step by step R and Python code is the opposite case, so it runs better on fewer, faster CPU cores.

“How would you do the following?”

“1. Find all running JupyterHub processes that belong to the user alexkgold.”

ps aux lists every process with its owner, and grep narrows it down:

ps aux | grep jupyterhub | grep alexkgold

Each | passes one command’s output to the next, and each grep keeps fewer lines:

ps -u alexkgold lists only that user’s processes, so ps -u alexkgold | grep jupyterhub gets to the same place. Our instance doesn’t run JupyterHub, but the same pattern finds the app from Installing a Real Application, which runs as its service account:

ps -u baseball-trajectory -o pid,%cpu,%mem,cmd

If one of these processes is running away with the CPU, its PID goes to kill. For a systemd service, sudo systemctl restart is the better tool.

“2. Find the different disks attached to your server and see how full each one is.”

lsblk lists the disks and partitions, and df -h shows how full each mounted filesystem is:

lsblk
df -h

On an EC2 instance the root EBS volume usually shows up as nvme0n1, mounted at /. -h prints sizes in K, M, and G instead of blocks.

lsblk shows the whole tree, including partitions that aren’t mounted; df -h reports only the mounted ones. On an AL2023 instance the tree usually looks like this:

“3. Find the biggest files in each user’s home directory.”

du measures sizes, sort -rh puts the biggest first, and head keeps the top of the list. Home directories belong to other users, so this needs sudo:

sudo du -ah /home | sort -rh | head -n 20

-a includes files, not just directories. To get a short list per user instead of one combined list, loop over the home directories:

for d in /home/*; do
  echo "== $d"
  sudo du -ah "$d" | sort -rh | head -n 5
done

Recap

  1. CPU speed, core count, RAM, and storage each limit a different kind of work. A GPU helps only with parallel work that the code is told to send to it.

  2. RAM runs out first for most data science work. Data takes more room in memory than on disk, so plan for about three times the largest dataset.

  3. Extra cores help only when a job splits into independent pieces, and most R and Python code has to be told to use them.

  4. ps, lsblk, df -h, and du show what a server is running and where its storage went. Resizing the instance is covered in Instance Size.
